# C1: cuBLASLt's NVFP4 GEMM vs the cuTile FP4 GEMM (2026-11-14)

Workstream C1 (branch `ws/c1-cublaslt-fp4`): before anyone hand-writes a cuda-oxide FP4 GEMM, find out whether
cuBLASLt's block-scaled FP4 GEMM beats the cuTile `gemm_nvfp4_raw` the nvfp4 engine runs.

**Result.** cuBLASLt 13.8 supports NVFP4 (e2m1 A/B, `VEC16_UE4M3` block scales) on sm_121 and is **1.35-1.5x
faster than cuTile as a raw GEMM** (338-383 vs 233-265 TFLOP/s at the MLP shapes). Its numerics are the same:
**bit-identical to the cuTile GEMM** on every output we compared (16.8M synthetic outputs; the whole nvfp4 engine on
96 corpus steps; all 278 eval responses), and a pinned algorithm is batch-invariant. It has no SiLU·mul epilogue,
so for gate/up the cuTile GEMM with SiLU·mul + quantize fused in (F1) stays faster; the win is the **down
projection**. With the down GEMM on cuBLASLt the whole MLP per layer is **10.3-10.8% faster at 16k** (the 10% bar of
this workstream, met narrowly) and the engine forward **3.1% faster at 16k** (1,940 → 1,881 ms per replayed step,
8,441 → 8,708 packed tok/s; 2.0-3.4% at 1k-32k), with logits bit-identical to before. Integrated as
`--fp4-gemm cutile|cublaslt` (`EngineOptions::fp4_gemm`, `$SYSONE_FP4_GEMM`); **every gate passes**, so it is the
**default on sm_121** (cuTile stays the default on every other architecture until measured there).

## 1. Support status (this machine: CUDA 13.4, cuBLASLt 13.8.0.4, driver 580.178.04, GB10 sm_121)

`bench_fp4_cublaslt --probe` (cudarc 0.19.2's bindings already carry every enum needed: `CUDA_R_4F_E2M1`,
`CUBLASLT_MATMUL_DESC_{A,B}_SCALE_MODE`, `CUBLASLT_MATMUL_MATRIX_SCALE_VEC16_UE4M3`):

| shape (engine `y [T, N] = x [T, K] · W [N, K]ᵀ`) | T = 1k | T = 16k | per-column alpha vector |
|---|---|---|---|
| gate/up N = 24576, K = 4096 | 7 candidates | 8 | `CUBLAS_STATUS_NOT_SUPPORTED` |
| gate or up half N = 12288, K = 4096 | 8 | 8 | not supported |
| down N = 4096, K = 12288 | 8 | 8 | not supported |

- Form: issued column-major as `yᵀ = W · xᵀ` (A = W op T, B = x op N), the "TN" layout FP4 requires; fp32 compute
  and scale type, bf16 D (= C, beta 0). Every candidate the heuristic returns at 16k is split-K-free and needs no
  workspace (some 1k candidates use split-K).
- **Scale layout.** cuBLASLt wants each block-scale tensor in its tiled layout: 128 rows x 4 scale columns per
  512-byte block, column blocks fastest, row `r` column `c` at byte `(r % 32)·16 + (r % 128 / 32)·4 + c % 4`
  (`kernels::nvfp4::lt_scale_offset`), not the row-major `[rows, K/16]` the checkpoint and our quantize kernels
  produce. Weights: re-laid out once at load (host round trip, 96 MiB extra for the 32 down projections).
  Activations: a new cuTile kernel `scales_to_lt` (a `[128, 4]` tile load, `reshape` + `permute` + store of one
  512-byte block per tile block; pure data movement), 0.12 ms per down GEMM at 16k.
- **Epilogue.** `D = alpha · Σ(q_x s_x)(q_w s_w)`, one bf16 rounding: exactly our `bf16(acc · alpha)` with the host
  scalar `alpha = 1/(igs·wgs)`. A per-output-column alpha (the device-vector pointer modes) is not supported for
  FP4, so the fused gate/up projection, whose halves have different `wgs`, takes two calls (gate, up; each its own
  scalar alpha) into the two column halves. Bias and the GELU/ReLU epilogues exist; there is no SiLU-gated
  (SwiGLU) epilogue, and the FP4-output mode (`D_OUT_SCALE`) quantizes D itself, not `silu(g)·u`.
- sm_120: not run (no such card here). cuBLAS documents block-scaled FP4 for sm_100 and sm_120; the x86 note
  (end) asks for the probe there.

## 2. Speed (`bench_fp4_cublaslt --tokens 1024,4096,16384,32768`, idle GPU, lock held, ms per launch)

Synthetic weights and activations at elephant-1's shapes (activations quantized by the engine's own kernel).
Two runs back to back; the second run's numbers (the first agrees within 1-2%):

| T | cuTile gate/up raw | cuTile fused gate/up (engine) | cuTile down (engine) | cuBLASLt gate/up (2 calls, pinned) | cuBLASLt down (pinned, 128x256) |
|---:|---:|---:|---:|---:|---:|
| 1,024 | 0.786 (262 TFLOP/s) | 0.800 | 0.414 (249) | 0.612 (337) | 0.300 (344) |
| 4,096 | 3.096 (266) | 3.143 | 1.598 (258) | 2.439 (338) | 1.189 (347) |
| 16,384 | 13.025 (253) | 13.530 | 6.682 (247) | 9.836 (335) | 4.371 (377) |
| 32,768 | 26.658 (247) | 27.306 | 13.175 (250) | 19.495 (338) | 8.700 (379) |

Every algorithm the heuristic returns was timed (full listing in the bench output). Gate/up: algorithm 70 (128x128
tile) is both the heuristic's first and the fastest (341-346 TFLOP/s); algorithm 67 variants 320-330; two variants
(custom options 143, 144) run at 90-160. Down: the heuristic's first split-K-free candidate (algorithm 67, 128x128,
custom option 23) gives 334-350 TFLOP/s; **algorithm 67 with the 128x256 tile, custom option 23** is the fastest at
4k-32k (355-383). A split-K candidate is fastest only at 1k for down (354 vs 337; not usable: not batch-invariant).

**Whole MLP per layer** (everything that differs between the paths; the residual add + norm + quantize before
gate/up is common to all): extra work cuBLASLt needs is the scale re-layout of the gate/up input (`[T, 256]`,
0.03 ms at 16k) and of the down input (`[T, 768]`, 0.12 ms), and, for a cuBLASLt gate/up, the separate
`silu_mul_nvfp4` (F1 tuning, 3.98 ms at 16k) that the cuTile path does in its GEMM epilogue.

| T | cuTile (engine): fused gate/up + down | all cuBLASLt: gate/up + `silu_mul_nvfp4` + down + 2 re-layouts | **hybrid: cuTile fused gate/up + cuBLASLt down + re-layout** |
|---:|---:|---:|---:|
| 1,024 | 1.214 | 1.177 (-3.0%) | 1.108 (-8.7%) |
| 4,096 | 4.741 | 4.640 (-2.1%) | 4.357 (-8.1%) |
| 16,384 | 20.212 | 18.417 (-8.9%) | **18.023 (-10.8%)** |
| 32,768 | 40.481 | 36.656 (-9.4%) | 36.405 (-10.1%) |

(run 1: hybrid -8.1 / -8.1 / **-10.3** / -10.0%.) Writing the down GEMM's input scales directly in the tiled layout
(from the fused gate/up GEMM's epilogue, whose `[128, 64]` output tile has exactly one 128x4 scale block) would
remove the re-layout: hybrid -10.9% at 16k. A cuBLASLt gate/up loses because `9.8 + 4.0 > 13.5` ms: the raw GEMM is
27% faster but SiLU·mul + quantize then costs a memory round trip of the bf16 `[T, 24576]` tensor (805 MB at 16k).

## 3. Correctness

`bench_fp4_cublaslt --check` (64 rows; f64 reference = the exact `alpha · Σ e2m1·s_x·e2m1·s_w` of the dequantized
operands; bf16 ulps against `bf16(reference)`):

| shape | cuTile vs bf16(exact) | cuBLASLt (pinned) vs bf16(exact) | cuBLASLt vs cuTile | \|rel err\| in 2^-8 units, both (p50 / p99 / max) |
|---|---|---|---|---|
| gate/up [64, 4096] x [24576, 4096]ᵀ (1.57M outputs) | 100.00% 0 ulp, max 1 | 100.00% 0 ulp, max 1 | **0 ulp everywhere** | 0.347 / 0.886 / 0.996 |
| down [64, 12288] x [4096, 12288]ᵀ (262k) | 99.99% 0 ulp, max 1 | 99.99% 0 ulp, max 1 | **0 ulp everywhere** | 0.348 / 0.888 / 1.868 |

Every other algorithm the heuristic returns (6 per shape, including the split-K ones at 1k) is also 0 ulp from
cuTile on these rows. Both kernels sum exact fp32 products (block scales applied inside the MMA) in fp32; the
outputs are their f64 value rounded once to bf16 except for ~0.01% of outputs within an accumulation error of a
rounding boundary, and there the two kernels round the same way. `tests/kernels_nvfp4_c1.rs` checks the engine's
own path (`Blas::gemm_nvfp4_lt` + the re-layout kernel) at T = 1024: **0 of 4.19M (down) and 0 of 12.6M (gate
half) outputs differ from the cuTile GEMM** (the test allows 1 ulp).

**Batch invariance** (as L1 did for bf16): the pinned algorithm's output rows for rows 0..64 are bit-identical at
T = 64, 300, 1024 and 4096, and rows `r..r+64` moved to row 0 of a 300-row call (r = 1, 3, 128, 1000) are
bit-identical to the same rows inside the 4096-row call; the same holds for every other split-K-free algorithm
(bench), and in `kernels_nvfp4_c1` for 1-, 37-, 129-, 300- and 324-row calls at offsets 0, 5, 128, 700 vs the
1024-row call (both shapes). No split-K means each output element is one fp32 dot product over K in an order fixed
by the kernel's K tiling; the scale tiles are addressed by row, so a row's position in the batch changes nothing.

## 4. Integration (`--fp4-gemm cutile|cublaslt`; default cublaslt on sm_121, cutile elsewhere)

- `EngineOptions::fp4_gemm: Option<Fp4Gemm>` (`None`: `$SYSONE_FP4_GEMM`, else `Fp4Gemm::default_for_arch`:
  cuBLASLt on sm_121, cuTile elsewhere; the resolved choice and its reason are logged and kept in `opts`),
  `sysone --fp4-gemm`, `bench_forward --fp4-gemm`, `FP4_GEMM=cublaslt
  reference/eval/run_sysone.sh` (passed as `--fp4-gemm`, so it is recorded with the server flags). The bf16 engine
  ignores it.
- Scope: the MLP **down** projection (`GraphOp::GemmNvfp4` on a projection whose `Linear::Nvfp4::lt_scales` was
  built at load, `ModelWeights::add_lt_scales_down`). Gate/up stays cuTile (fused, or raw with
  `--nvfp4-separate-silu`). The graph is unchanged; the executor runs `scales_to_lt` into a fixed scratch owned by
  `Blas` (sized for the largest bucket, 24 MiB at 32k; one buffer for every call like the cuBLAS workspace: the
  forward's ops run in order on one stream) and then `Blas::gemm_nvfp4_lt`.
- Algorithm: cuBLASLt's heuristic at 16,384 rows, split-K-free candidates only; the preferred entry of a small fixed
  table (`FP4_PREFERRED`: on sm_121 for `[4096, 12288]` algorithm 67, tile 128x256, custom option 23, the measured
  fastest), else the first candidate (L1's rule). Chosen once per weight shape, used at every T (layouts per T
  checked with `cublasLtMatmulAlgoCheck` before graph capture). No timing at load: the choice is deterministic.
- Memory: +96 MiB of weight scales and the 24-48 MiB scratch.

## 6. Decision

The integration criterion (whole MLP ≥ 10% faster at 16k with a batch-invariant pinned algorithm) is met by the
hybrid (10.3% and 10.8% in two runs), so the option is integrated, and every gate passes with it. It is faster in
the engine at every bucket (2.0-3.4%), its logits are bit-identical to the cuTile engine (96/96 corpus steps, 278/278
eval responses), and it stays batch-invariant (164/164, 155/155). So it is **the default on sm_121**
(`Fp4Gemm::default_for_arch`). Elsewhere the default stays cuTile: FP4 support, the fastest algorithm and the
whole-MLP balance on sm_120 are unmeasured (section 8), and a cuBLASLt that refuses FP4 there would fail the
engine's first forward. `--fp4-gemm cutile` (or `SYSONE_FP4_GEMM=cutile`) restores the previous kernel exactly.

Not done, and why:
- **cuBLASLt for gate/up**: slower as a whole (-8.9% MLP vs -10.8% for the hybrid at 16k): no SwiGLU epilogue.
- **Re-layout fused into the producer** (the fused gate/up GEMM writing its scale tile in cuBLASLt's layout): ~0.6%
  of the MLP, 4 ms per forward at 16k; it would change the F1 kernel's output layout, a separate change.
- **Interaction with workstream S2** (residual add in the down GEMM's epilogue, in progress on another branch):
  S2 replaces the down `GemmNvfp4` by a cuTile GEMM that also adds the residual. cuBLASLt can add a C matrix
  (`beta = 1`, C = residual), but it computes `alpha·acc + residual` in fp32 with one bf16 rounding, while the
  engine (and S2's kernel) computes `bf16(bf16(acc·alpha) + residual)`: not bit-identical, so the two cannot be
  combined without changing outputs. After both merge, `GemmNvfp4` (and so this path) applies only when S2's fusion
  is off; the choice between them is cuBLASLt down (64 ms at 16k here) vs the fused residual add (S2's estimate
  ~18 ms, PROFILE.md #4). Whoever merges the second must pick one per architecture with a measurement.

## 7. Is a hand-written cuda-oxide FP4 GEMM (`mma.sync` block-scaled e2m1) still worth it?

**Yes, but only for gate/up, and the target is now concrete.** The counters say what limits the cuTile kernels: the
same `mma.sync` block-scaled instruction runs at 55-57% tensor-pipe activity in cuTile and at 72-85% in cuBLASLt.
From the profile, 100% tensor-pipe activity at the MLP shapes is about 460 TFLOP/s on GB10 (cuTile's down: 250
TFLOP/s at 56.6%). cuBLASLt's best kernels reach 340-383 (74-83% of that), and its down kernel is already within
~15% of the ceiling.

- **Down projection: not worth hand-writing.** cuBLASLt (now the sm_121 default) leaves at most ~15% (≤ 0.6 ms
  per layer, ≤ 20 ms per forward at 16k, ~1%) to a perfect kernel.
- **Gate/up with SiLU·mul + quantize fused: worth it.** This is the one place cuBLASLt cannot go, and it is the
  largest single op left (422-428 ms per forward at 16k, 56% tensor pipe). A hand-written kernel at cuBLASLt's
  gate/up efficiency (algorithm 70: 341-346 TFLOP/s, 72-78% pipe) with F1's epilogue would take it from 13.2-13.5
  to ~9.7-10 ms per layer: **~110 ms per forward at 16k (5.5-6%)**, about twice what C1 gained. 400 TFLOP/s (87%,
  above anything measured here) would give ~150 ms.
- **How** (from the kernel names and counters): the fast kernels are `nvjet_sm121_..._tmaAB` (TMA loads of the
  e2m1 operands and the tiled scales, 3 stages, 128x256 or 256x128 tiles, 8 warps) and CUTLASS
  `sm120_bstensorop_s16864gemm_block_scaled` (`mma.sync.m16n8k64` with ue4m3 scales, 128x128, 12 warps). A
  cuda-oxide kernel would copy that structure: a warp-specialised TMA producer, 3-4 stage smem ring, consumer warps
  issuing the same block-scaled `mma.sync` in F1's K order, and F1's epilogue on interleaved gate/up rows. Bit
  identity with the current engine is likely (cuBLASLt and cuTile already agree bit for bit; the per-element chain
  is the same instruction in the same K order), and `kernels_nvfp4_f1` plus `c1_fp4_gemm_cublaslt_vs_cutile`-style
  engine comparisons are the harness. Using the tiled scale layout (`lt_scale_offset`) for both operands lets TMA
  load scale tiles contiguously, which is the k-tile-major idea of PROFILE.md #2 in the form NVIDIA's kernels use.
- Cheaper first experiment before cuda-oxide: give the cuTile fused kernel the cuBLASLt structure it can express
  (a 3-stage `num_stages` hint / `latency` hints on the loads, a 128x256 tile with interleaved rows) and re-measure
  the tensor pipe. F1 found no knob that moved the raw kernel, so expect the hand-written kernel to be needed.

## 8. x86 (sm_120)

Nothing about FP4 support was run on sm_120 (the engine keeps cuTile as its default there). T8 in docs/x86/TASKS.md gets item 5: the probe, the check and the
timing of `bench_fp4_cublaslt` per card, `kernels_nvfp4_c1` (added to `scripts/x86/run_tests.sh`), and with the
checkpoint `SYSONE_FP4_GEMM=cublaslt engine_e2e_nvfp4` and `bench_forward --fp4-gemm cublaslt`. `FP4_PREFERRED` has
no sm_120 entry, so there the heuristic's first split-K-free candidate is used until the card's fastest is known.
On discrete Blackwell with ~1.8 TB/s (RTX PRO 6000) the separate `silu_mul_nvfp4` costs far less than on GB10's
~250 GB/s, so a full cuBLASLt MLP may win there where it loses here; the bench reports both.
