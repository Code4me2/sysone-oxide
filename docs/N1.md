# N1: NVFP4 end to end in the engine (2026-11-13)

Workstream N1 (branch `ws/n1-nvfp4-engine`) runs the NVFP4 checkpoint (`Code4me2/elephant-1-NVFP4-MLP`, W4A4 on
the 96 MLP projections, DESIGN §3.1) in the real engine: the MLP GEMMs run on W3c's block-scaled FP4 kernels,
activations are quantized exactly as compressed-tensors does, and everything else is the bf16 engine (SIMT GDN by
default on sm_121, CUDA graphs per T bucket). It passes the committed `[eval.nvfp4]` gate against all four NVFP4
QDQ reference paths, the end-to-end `[nvfp4]` gate, and a new `[batch_invariance.nvfp4]` gate that was derived
from reference-only data and committed before the engine was evaluated. At 16k packed tokens the forward is
**1.48x faster** than bf16: 2,086 ms against 3,078 ms (7,850 against 5,320 tok/s).

## What changed

- **Engine.** `sysone --engine nvfp4 --model <NVFP4 checkpoint>`. The checkpoint must match the engine: `--engine
  nvfp4` on a bf16 checkpoint (or `bf16` on an NVFP4 one) fails before any weight is read, and after the load
  every MLP projection must be NVFP4 and nothing else (`check_weight_format`; `forward::build` refuses NVFP4
  outside the MLP). `/metrics` exports `sysone_engine_info{engine="nvfp4",...}`. `EngineOptions::weights`
  (`None`: follow the checkpoint), `EngineOptions::nvfp4_fused`; `$SYSONE_ENGINE=bf16|nvfp4` in `engine_e2e`.
- **Forward** (`forward::build_with`). Per layer the MLP becomes
  ```text
  q1, s1 = add_zc_rmsnorm_nvfp4(x += o, ln2)   residual add + norm, bf16 rounding, quantize under gate/up's input_global_scale
  gu     = gemm_nvfp4(q1, s1, [Wgate; Wup])     block-scaled FP4 GEMM, epilogue 1/(a_gs·w_gs) per half
  q2, s2 = silu_mul_nvfp4(gu)                   SiLU·mul with both bf16 roundings, quantize under down's input_global_scale
  m      = gemm_nvfp4(q2, s2, Wdown)
  ```
  The quantization is fused into the epilogue of the preceding op. `--nvfp4-unfused` (`nvfp4_fused = false`)
  materialises the bf16 norm and SiLU·mul outputs and runs W3c's standalone `quantize_nvfp4` instead.
- **Kernels** (`src/kernels/nvfp4`). `zc_rmsnorm_nvfp4`, `add_zc_rmsnorm_nvfp4` (one row per tile block, the same
  fp32 operations as `kernels::norm`, then `nvfp4_quantize_tile` on the bf16-rounded row) and `silu_mul_nvfp4`
  (1,024 columns per tile block). `gemm_raw_op` launches the production `Raw` GEMM on the device-resident
  checkpoint weights (`Linear::Nvfp4`, unchanged layout) with the scalar per-half epilogue `RawAlpha`, computed
  from each part's `weight_global_scale` exactly as `prepare_weights` does (unit test). GEMM tiles are
  `GemmTiles::DEFAULT` (128x128x128, grouped-M 8) at every T, so a row's result does not depend on its batch.
- **Fusion is bit-exact.** `tests/kernels_nvfp4_fused.rs`: each fused kernel equals its bf16 op followed by the
  standalone quantize byte for byte (packed values, scales and the updated residual; K = 4096 and 12288, rows over
  2^-8..2^8 with zero rows, three activation global scales including one that saturates the e4m3 scale): 0
  mismatches. End to end, `engine_e2e::nvfp4_fused_equals_unfused`: 84/84 steps (42 batches, eager and replay)
  give bit-identical logits with and without the fusion.
- **Per-checkpoint profile** (DESIGN §13 item 9). `ModelConfig::profile` reads `quantization_config.format`:
  no quantization → bf16 engine, qev's limits (32,768 per branch, 65,536 per request); `nvfp4-pack-quantized` →
  nvfp4 engine, **16,384 tokens per branch**, 65,536 per request; any other format is refused. The server's
  `--max-branch-tokens` / `--max-request-tokens` now default to the profile (flags still override, with a warning
  above the profile). The 16,384 is applied per branch (prefix + one question), not to the request total as
  §13 item 9 first proposed: E1 established that the checkpoint's own evaluation applies its limit per evaluated
  question (`reference/eval/README.md`, "Eligibility"), and a request total of 16,384 would refuse eval records
  the reference answered.
- **Harness.** `ENGINE=nvfp4 bash reference/eval/run_sysone.sh` (records every weight shard's sha256);
  `bench_forward` follows the checkpoint (`--nvfp4-unfused`); `scripts/x86/run_tests.sh` runs
  `kernels_nvfp4_fused` everywhere and `engine_e2e_nvfp4` with `--nvfp4`.

## Gates

### The new gate, committed first

`[batch_invariance]` (bf16) has the bf16 reference's own batch dependence as its envelope, which says nothing about
FP4 activation rounding. Its NVFP4 counterpart `[batch_invariance.nvfp4]` uses the NVFP4 QDQ reference's own batch
dependence: the shared-prefix batched fork vs sequential branches on the 52-request model corpus (`noise_stats.py`
group `nvfp4_fork`, already in `noise_report.json`'s pairs), factor 1.5: `dp_max` 0.2547 (measured 0.1698),
`dlogit_max` 1.665 (measured 1.110). It was committed (`441827f`) before sysone NVFP4 ran; re-rendering
`tolerances.toml` with the generator adds only this table. No existing gate, threshold or tolerance changed. The
end-to-end probability gate `[nvfp4]` already existed (W1b) and is used unchanged.

### Batch invariance and graph replay

| check | nvfp4 | bf16 (same build) |
|---|---|---|
| alone vs packed (16k budget): branches bit-identical; max \|dp\| | 103/164; 7.93e-2 | 103/164; 1.096e-2 |
| alone vs alone in a 4x larger bucket: bit-identical; max \|dp\| | 134/155; 1.1e-6 | 134/155; 2.1e-6 |
| gate | `[batch_invariance.nvfp4]` 0.2547: **PASS** | `[batch_invariance]` 0.01822: PASS |
| graph replay vs eager (7 batches + 1 interleaved) | bit-identical | bit-identical |

The same branches are bit-identical in both engines (103/164): the NVFP4 GEMM and the quantization are
batch-invariant, so the non-identical branches come from the parts the two engines share (the bf16 cuBLAS
projections pick algorithms per M, as in bf16). FP4 activation rounding amplifies those bf16-level differences
~7x (max 7.9e-2), which the bf16 gate (0.0182) would not allow; the NVFP4 gate, from the QDQ reference's own
batch dependence (0.17 measured), does. Pinning cuBLAS algorithms per bucket (PHASE2A open item 3) would make the
NVFP4 engine fully batch-invariant at no cost to the gate.

- GEMM time at 16k: 2,347 ms (all bf16) → 1,339 ms (bf16 non-MLP 707 + FP4 MLP 633), 1.75x; the FP4 GEMMs run at
  248 (gate/up) and 255 (down) TFLOP/s against cuBLAS bf16's ~97. GEMMs are now 64% of the forward (bf16: 76%);
  the bf16 GDN in-projection (410 ms) is the largest single op.
- Fusion saves 121 ms at 16k (5.5%), 33 ms at 4k, 11 ms at 1k, all bit-identical. The fused SiLU·mul + quantize
  (203 ms at 16k) is slower than the plain `silu_mul` (179 ms); the saving comes from the fused add + norm +
  quantize (75 ms, against 78 ms for the same 32 norms alone) and from dropping the standalone quantize launches
  (127 ms). Tuning `silu_mul_nvfp4` (several rows per tile block) is the next step there.
- Memory: 8.3 GiB of weights (bf16: 14.8 GiB), arena 1.04 GiB at a 16k largest bucket (bf16 1.50).
- First step (JIT) 6.0 s at 1k (bf16 4.7 s).

**Eval wall time** (278 records, one request at a time over HTTP, server already loaded): 108 s for the nvfp4
engine, against 150 s for bf16 with SIMT (E2); load + warm-up of the server 9.1 s.

## Open items

1. Batch invariance: pin cuBLAS algorithms per bucket for the bf16 projections, so the NVFP4 engine's packed
   results become bit-identical to alone (today 103/164 branches, the same as bf16).
2. `silu_mul_nvfp4` tuning (above); the next large costs are the bf16 GDN in-projection (410 ms at 16k) and the
   GDN scan (343 ms). Done in F1 (docs/F1.md): SiLU·mul + quantize now runs in the gate/up GEMM's epilogue at no
   cost, and `silu_mul_nvfp4` itself (still used with `--nvfp4-separate-silu`) runs at 231 GB/s instead of 149.
3. Wider quantization (attention / GDN projections) needs a new checkpoint and its own gates (DESIGN §11 Phase 3).
4. sm_120 (x86): the NVFP4 engine and the fused kernels have run only on sm_121. The x86 T4 task now includes the
   engine when the user provides the checkpoint there; GEMM tiles were tuned on GB10 only.
5. sm_90 has no FP4 MMA: the dequantize-at-load fallback (PLATFORM.md) is not implemented, so the nvfp4 engine
   is not expected to run there (untested).
