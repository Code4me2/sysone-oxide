# G1: GatedDeltaNet in cuda-oxide (2026-11-13)

Workstream G1 moved the hot part of the GDN mixer (the WY/triangular solve and the chunk scan) from cuTile to
SIMT kernels written in Rust with cuda-oxide (`kernels-simt/`), on the tensor cores via `mma.sync`. The cuTile path
stays as the fallback and as the test reference; `GdnBackend::{Tile, Simt}` selects the implementation and
`Tile` is still the default (see "Default" below).

## Results (idle GPU, `scripts/gpu.sh ./target/release/bench_gdn --backend {tile,simt} --iters 20`)

GDN mixer per layer (conv, gates/prep, delta rule, gated norm; excluding the in/out projections), ms. Trees are
one prefix plus 8 suffixes of 100 tokens per request (`bench_gdn` default shapes).

| T | prefix | tile | simt | speed-up | target |
|---:|---:|---:|---:|---:|---:|
| 1,024 | 224 | 3.99 | **0.76** | 5.2x | <= ~1 |
| 4,096 | 2,048 | 14.88 | **2.96** | 5.0x | <= ~3 |
| 16,384 | 2,048 (6 requests) | 58.5 | **11.2** | 5.2x | <= ~10 |
| 16,384 | 15,584 (1 request) | 56.6 | **12.7** | 4.5x | <= ~10 |

Over 24 layers at 16k: 1.40 s -> 0.27 s (GDN share of the GEMM + GDN forward: 38% -> 10%).

Per-kernel breakdown, SIMT, ms (each launch timed alone):

| T | conv (tile) | gates | tinv | scan prefix | scan suffix | norm (tile) |
|---:|---:|---:|---:|---:|---:|---:|
| 1k | 0.16 | 0.003 | 0.09 | 0.09 | 0.28 | 0.10 |
| 4k | 0.68 | 0.004 | 0.35 | 0.92 | 0.61 | 0.48 |
| 16k (2k prefixes) | 2.73 | 0.008 | 1.31 | 3.54 | 1.68 | 1.94 |
| 16k (15.6k prefix) | 2.65 | 0.008 | 1.30 | 6.39 | 0.29 | 1.97 |

The 1k and 4k targets are met; 16k misses by ~12% (2k prefixes) and ~27% (one 15.6k prefix). What limits it:

- **conv + gated norm are 4.7 ms of the 11.2** and are cuTile kernels already at DRAM bandwidth (conv moves 536 MB
  at ~205 GB/s, the norm 402 MB at ~205 GB/s; the GB10 copy roofline is 221 GB/s). They can only get faster by
  fusion. Fusing the norm into the scan (whole-head CTAs of 8 warps, norm in the epilogue) was tried and was slower
  overall (11.3 ms: the epilogue lengthens the sequential per-chunk chain). The promising next step is fusing the
  conv into its consumers (tinv and scan read the projection output, apply the 4 taps with the tree halo from the
  chunk table, round to bf16): it removes the conv kernel and its 268 MB write, estimated -1.5 ms at 16k.
- **The prefix scan is latency-bound for long prefixes**: one CTA per (segment, head, 64 value columns) walks the
  segment's chunks in order, so a single 15.6k prefix gives 64 CTAs for 48 SMs (16 SMs run two) and ~26 us per
  chunk. Removing the Tinv global loads (an experiment with fake data) saved ~1 ms of scan time; staging Tinv in
  shared memory with cooperative loads cost more in barriers than it saved. The kernel uses 255 registers with
  ~270 B of spills; Nsight Compute could not be used (no permission for GPU performance counters on this machine).
- tinv is bandwidth-bound (reads k, writes 2.5 KB of Tinv per chunk and head).

## Design

Per layer the SIMT mixer runs: `tree_conv1d_silu` (cuTile) -> `gdn_simt_gates` -> `gdn_simt_tinv` ->
`gdn_simt_scan` (prefix phase) -> `gdn_simt_scan` (suffix phase) -> `gated_rmsnorm` (cuTile). Segment semantics are
those of the cuTile path: chunks restart at each segment start, suffixes start from their parent's final state
(read-only), prefixes write theirs to `GdnScratch::state`, grids depend only on the plan's capacities.

- **No stored WY intermediates.** The cuTile path writes w, u, qd, kd (f32 `[T, 4096]` each) and p, which at 16k is
  ~1.2 GB of traffic. The SIMT scan recomputes everything per chunk from the conv output and Tinv:
  `X = k S`, `v_new = Tinv (beta (v - e^cum X))`, `o = e^cum q S + P v_new`, `S = e^(sum g) S + k^T (e^rc v_new)`,
  with P = (q k^T ⊙ decay) recomputed in the scan. Only Tinv (lower 16x16 blocks) goes through memory.
- **q and k are never normalised in memory.** They are the conv output (bf16, exact) times a per-row scale, so
  `k k^T`, `q k^T`, `k S`, `q S` use the raw bf16 rows as one exact MMA operand and apply the scales in fp32.
  `gdn_prep` is replaced by a gates-only kernel (1.9 ms -> 0.01 ms at 16k), and the SIMT scratch does not allocate
  q, k, w, u, qd, kd, p (`GdnScratch::for_backend`, ~1.2 GB less at 16k).
- **fp32 accuracy on bf16 tensor cores.** fp32 operands are split `x = hi + lo` into two bf16 (residual <= 2^-17
  relative); a product with one exact operand costs 2 MMAs, fp32 x fp32 costs 3 (hi·hi + hi·lo + lo·hi). bf16
  `m16n8k16` runs at ~104 TFLOP/s on GB10 against ~57 for tf32, and 3xTF32 (what cuTile does) costs 3 tf32 MMAs.
- **Register-resident transposed state.** Each warp owns 16 value rows of `S^T` as MMA accumulators; two adjacent
  `m16n8` C tiles are exactly one `m16k16` A fragment, so each product's output feeds the next without shared
  memory. Shared memory holds the k tile, the split P, an output staging tile and per-row scalars (47 KB, 2 CTAs/SM).
- **Triangular solve**: blocked 16x16 forward substitution in fp32 SIMT (diagonal blocks in registers, one warp
  each; then the three block rows), after an exact bf16 Gram `k k^T`.
- **Grid order**: the CTAs that read the same k-head rows (2 v-heads x 2 value blocks) are adjacent so the rows come
  from DRAM once.

### Accuracy (tests/kernels_gdn.rs, tree batch of 3,062 tokens / 20 segments)

| check | tile | simt | tolerance (2x transformers' f32 envelope) |
|---|---|---|---|
| scan output vs f64 recurrence | 99.94% exact, 0 over | 99.77% exact, 0 over | 1 bf16 ulp + 5e-4 x (segment, head) rms |
| prefix 0 final state, max abs (rms 5.65e-2) | 3.6e-6 | 5.8e-6 | 1.7e-5 (3e-4 x rms) |
| Tinv vs f64 inverse, max / row max | 4.4e-5 | 3.4e-5 | 1e-4, and simt <= 1.5x tile |

The SIMT state error (~1.0e-4 x rms) is about transformers' own f32 error on these inputs (1.1e-4 x rms, measured by
W3a) and inside the gate (2x that); the cuTile path, with 3xTF32 everywhere, is at ~60% of it (6.4e-5 x rms). Where more margin
is needed, `k S` (the term that feeds the recursion) can take a 3-way split of S for ~12% more MMAs.

### Tests

All mixer tests run for both backends (`GDN_BACKENDS=tile,simt`, default both): stage-by-stage vs the f64
references, tree-batched vs each branch alone, `GdnPlan::update` and batch invariance (bit-identical), and the new
`graph_replay_matches_eager` (mixer captured once as a CUDA graph, replayed after `GdnPlan::update` for two
different trees, bit-identical to eager). `simt_tinv_matches_f64_reference` checks Tinv of both backends against
an f64 inverse. `tests/kernels_simt.rs` checks the artifact and the load/launch path.

### Default

`gdn_mixer` still runs the cuTile path; callers choose with `gdn_mixer_with(GdnBackend::Simt, ..)`. The SIMT path
passes every kernel-level gate, but DESIGN §1 keeps the most precise variant as the default until the end-to-end
gate (§9.2) has run with the faster one, and the engine does not run GDN layers yet (I1). Flip the default for
sm_121 once that gate passes.

## Build (kernels-simt/, see its README)

- `kernels-simt/` is a standalone cuda-oxide crate pinned to Rust 1.99.1 (its own `rust-toolchain.toml`); it
  depends on `cuda-device` by path into `../cuda-rust/cuda-oxide`. sysone stays on 1.98.0 and never compiles it.
- `kernels-simt/build.sh [ARCH]` (default `sm_121`) runs `cargo oxide build --arch ARCH`, copies the PTX to
  `kernels-simt/artifacts/gdn_simt.<ARCH>.ptx` and writes a manifest with the sha256 of the kernel sources
  (Cargo.toml, Cargo.lock, rust-toolchain.toml, src/) and of the PTX. It uses the published backend
  (`~/.cargo/cuda-oxide/librustc_codegen_cuda.so`) so cargo-oxide never builds inside `../cuda-rust`.
- **Policy: checked-in artifact, verified by hash.** sysone's `build.rs` embeds each artifact whose manifest matches
  the current sources and the PTX file. A stale or mismatched artifact is embedded as an error (and printed as a
  cargo warning); a missing one is simply absent. Selecting the SIMT backend then fails at run time with the exact
  rebuild command; nothing falls back to cuTile silently. Chosen over running cargo-oxide from `build.rs` because a
  nested cargo under the 1.98.0 build would need a second toolchain, a CUDA toolkit and the codegen backend on every
  machine that builds sysone, and a build script that sometimes rebuilds kernels makes builds depend on the host.
- Run time: `src/kernels/simt.rs` loads the PTX for the device's exact architecture once per device (the driver
  caches the JIT) and launches with cuda-async's `AsyncKernelLaunchBuilder` on the same stream as the cuTile
  kernels. Other architectures need their own artifact (`build.sh sm_100a`); arch is a parameter, not hard-coded.

## cuda-oxide notes (nothing modified upstream)

1. Loops around the `mma.sync` intrinsics are not unrolled by cuda-oxide's `opt -O2` (the intrinsic lowers to
   `asm sideeffect`), so register arrays indexed by the loop variable are demoted to local memory. Repro: a kernel
   with `let mut acc = [[0f32; 4]; 8]; for n in 0..8 { acc[n] = mma_m16n8k16_f32_bf16(acc[n], a, b) }` compiles to
   one `mma.sync` in a loop and a 128-byte `__local_depot`. Worked around with an `unroll!` macro (constant index
   per copy).
2. `cuda_core::Function::set_max_dynamic_shared_memory_bytes` is `pub(crate)`; raising the dynamic shared memory
   limit of an untyped (PTX-loaded) kernel needs `cuFuncSetAttribute` on `Function::cu_function()` directly
   (`SimtModule::function`).
3. `cargo oxide build` in a project with a path dependency on the cuda-rust checkout builds the codegen backend in
   place inside that checkout unless `CUDA_OXIDE_BACKEND` points at the published `.so`; `build.sh` sets it.
