# G1: GatedDeltaNet in cuda-oxide (2026-11-13)

Workstream G1 moved the hot part of the GDN mixer (the WY/triangular solve and the chunk scan) from cuTile to
SIMT kernels written in Rust with cuda-oxide (`kernels-simt/`), on the tensor cores via `mma.sync`. The cuTile path
stays as the fallback and as the test reference; `GdnOptions::backend` (`GdnBackend::{Tile, Simt}`) selects the
implementation and `Tile` is still the default (see "Default" below). G1 started before P1 (the cuTile GDN speed-up of
Phase 2a) was merged and was then merged onto it; every comparison below is against P1's cuTile path on `main`.

What limits 16k:

- **conv + gated norm are 4.5 ms of the 11.5** and are cuTile kernels already at DRAM bandwidth (conv moves 536 MB
  at ~205 GB/s, the norm 402 MB at ~205 GB/s; the GB10 copy roofline is 221 GB/s). They can only get faster by
  fusion. Fusing the norm into the scan (whole-head CTAs of 8 warps, norm in the epilogue) was tried and was slower
  overall (the epilogue lengthens the sequential per-chunk chain). The promising next step is fusing the conv into
  its consumers (tinv and scan read the projection output, apply the 4 taps with the tree halo from the chunk
  table, round to bf16): it removes the conv kernel and its 268 MB write, estimated -1.5 ms at 16k.
- **The prefix scan is latency-bound for long prefixes**: one CTA per (segment, head, 64 value columns) walks the
  segment's chunks in order, so a single 15.6k prefix gives 64 CTAs for 48 SMs and ~28 us per chunk. The kernel
  uses 255 registers with 296 B of spills; Nsight Compute could not be used (no permission for GPU performance
  counters on this machine).
- The fp32-grade state products (three-way splits, see "Accuracy") cost ~3% of the mixer against the two-way splits
  of the first version (11.0 -> 11.5 ms at 16k); dropping them for the `Tinv R` product alone saves ~0.2 ms but puts
  the state error above the cuTile path's on most prefixes, so it was not kept.

## Design

Per layer the SIMT mixer runs: `tree_conv1d_silu` (cuTile) -> `gdn_simt_gates` -> `gdn_simt_tinv` ->
`gdn_simt_slot_guard` -> `gdn_simt_scan` (prefix phase) -> `gdn_simt_scan` (suffix phase) -> `gated_rmsnorm`
(cuTile). Segment semantics are those of the cuTile path: chunks restart at each segment start, suffixes start from
their parent's final state (read-only), prefixes write theirs to `GdnScratch::state`, grids depend only on the
plan's capacities. `simt::chunk_scan` returns the same four operations as the cuTile scan (inverse, the WY slot,
prefix scan, suffix scan); the WY slot holds the slot guard.

- **No stored WY intermediates.** The scan recomputes everything per chunk from the conv output and Tinv:
  `X = k S`, `v_new = Tinv (beta (v - e^cum X))`, `o = e^cum q S + P v_new`, `S = e^(sum g) S + k^T (e^rc v_new)`,
  with P = (q k^T ⊙ decay) recomputed in the scan. Only Tinv (lower 16x16 blocks) goes through memory. (P1's cuTile
  scan adopted the same `v_new` form but still stores P.)
- **q and k are never normalised in memory.** They are the conv output (bf16, exact) times a per-row scale, so
  `k k^T`, `q k^T`, `k S`, `q S` use the raw bf16 rows as one exact MMA operand and apply the scales in fp32.
  The SIMT gates kernel computes g and beta only; the SIMT scratch (`GdnScratch::for_backend`) does not allocate q,
  k, w, u, qd, kd or p.
- **fp32 accuracy on bf16 tensor cores.** fp32 operands are split into bf16 parts. The products that feed the
  recurrent state (`k S`, `Tinv R`, `k^T Z`) use three-way splits `x = hi + mid + lo` (residual <= 2^-27, fp32
  grade): 3 MMAs with one exact operand, 6 for fp32 x fp32 (every term down to 2^-18 relative). The output-only
  products (`q S`, `P v_new`) use two-way splits (residual <= 2^-18): 2 and 3 MMAs; their errors do not compound
  across chunks. bf16 `m16n8k16` runs at ~104 TFLOP/s on GB10 against ~57 for tf32.
- **Register-resident transposed state.** Each warp owns 16 value rows of `S^T` as MMA accumulators; two adjacent
  `m16n8` C tiles are exactly one `m16k16` A fragment, so each product's output feeds the next without shared
  memory. Shared memory holds the k tile, the split P, an output staging tile and per-row scalars (47 KB, 2 CTAs/SM).
- **Triangular solve**: blocked 16x16 forward substitution in fp32 SIMT (diagonal blocks in registers, one warp
  each; then the three block rows), after an exact bf16 Gram `k k^T`.
- **Grid order**: the CTAs that read the same k-head rows (2 v-heads x 2 value blocks) are adjacent so the rows come
  from DRAM once.
- **State slots and graph replay.** The launchers check `num_prefixes <= scratch.slots`, but a CUDA graph replayed
  after `GdnPlan::update` does not repeat host checks. Graph users size the scratch with `GdnScratch::for_plan` (one
  slot per segment the plan can hold); if a replay still sees a segment whose slot is past the scratch,
  `gdn_simt_slot_guard` writes NaN over that segment's output (the scan skips it), so it fails loudly instead of
  leaving stale output (test `simt_replay_past_slot_capacity_is_nan`). The guard is a separate 2 us launch because
  folding the check into the scan raised its spills and cost ~0.6 ms at 16k.

| **worst** | **1.13e-4** | **6.5e-5** (prefix 0) | **3.6e-5** (prefix 0) | | |

- The gate (`gdn_kernels_match_f64_references_on_a_tree_batch`) is 2.2e-4 x rms on every prefix: twice
  transformers' worst error on the batch (1.13e-4, prefix 4). It was 3e-4 before this pass, which is looser than
  2 x 1.1e-4. Both backends pass with >= 3.4x margin; SIMT is below the cuTile path on every prefix.
- On prefix 0 (the only multi-chunk prefix longer than 200 tokens) both kernels exceed twice transformers' own
  error *on that prefix* (tile 10x, SIMT 5.8x), although they stay far below transformers' worst prefix. It is not
  the explicit chunk inverse nor the `v_new` form: a torch f32 emulation of the kernels' formulation (explicit
  `Tinv`, `v_new = Tinv (beta (v - e^cum k S))`, reverse-scan decays) gives 7.3e-6 on prefix 0, and
  `gdn_envelope.py`'s explicit-inverse variant of transformers gives 6.8e-6. The extra error is in the kernels'
  elementwise arithmetic (not yet identified) and is shared by both backends; it is recorded as an open item.
- The first SIMT version (two-way splits everywhere) reached 2.5e-4 x rms on prefix 3 (21x the cuTile path) and
  would fail the 2.2e-4 gate; the three-way splits of this pass fixed that.

Other checks, both backends (same tolerances as W3a/P1):

| check | tile | simt | tolerance |
|---|---|---|---|
| scan output vs f64 recurrence | 99.91% exact, 0 over | 99.80% exact, 0 over | 1 bf16 ulp + 5e-4 x (segment, head) rms |
| mixer chain from the projection | 0 over | 0 over | 4 bf16 ulp + 1e-2 x out rms |
| Tinv vs f64 inverse (entries the scans read), max / row max | 4.4e-5 | 3.4e-5 | 1e-4, and simt <= 1.5x tile |
| tree vs each branch alone (suffix scan, mixer) | 0 over | 0 over | as the scan / chain |

The f64 oracle of the SIMT run takes the exact f64 normalisation of the GPU conv output as q and k (the SIMT kernels
never store normalised q, k), so its q/k stage check is skipped and its normalisation is covered by the scan and
state checks.

### Tests

All mixer tests run for both backends (`GDN_BACKENDS=tile,simt`, default both): stage-by-stage vs the f64
references, tree-batched vs each branch alone, `GdnPlan::update` and batch invariance (bit-identical),
`graph_replay_matches_eager` (mixer captured once as a CUDA graph, replayed after `GdnPlan::update` for two
different trees, bit-identical to eager), `simt_tinv_matches_f64_reference`, and
`simt_replay_past_slot_capacity_is_nan`. `tests/kernels_simt.rs` checks the artifact and the load/launch path.
P1's tests (`scan_options_and_precision_variants_vs_f64`, `fused_conv_qk_matches_standalone_conv_and_prep`,
`scan_from_bf16_conv_matches_stored_f32_qk`) are cuTile-only and unchanged. compute-sanitizer on the SIMT path
(`plan_update_and_batch_invariance`, `simt_replay_past_slot_capacity_is_nan`): memcheck 0 errors, racecheck 0
hazards, synccheck 0 errors; initcheck was not run (it holds the shared GPU lock for more than 10 minutes).

### Default

`gdn_mixer` still runs the cuTile path; callers choose with `gdn_mixer_with(.., &GdnBackend::Simt.options())`. The
SIMT path passes every kernel-level gate and is now more precise than the cuTile path on every prefix of the test
batch, but DESIGN §1 keeps the default until the end-to-end gate (§9.2) has run with the faster variant, and the
engine (I1) wires the GDN kernels through its own op table, not `gdn_mixer`. Flip the default for sm_121 once
that gate passes.

## Build (kernels-simt/, see its README)

- `kernels-simt/` is a standalone cuda-oxide crate pinned to Rust 1.99.1 (its own `rust-toolchain.toml`); it
  depends on `cuda-device` by path into `../cuda-rust/cuda-oxide`. sysone stays on 1.98.0 and never compiles it.
- `kernels-simt/build.sh [ARCH]` (default `sm_121`) runs `cargo oxide build --arch ARCH`, copies the PTX to
  `kernels-simt/artifacts/gdn_simt.<ARCH>.ptx` and writes a manifest with the sha256 of the kernel sources
  (Cargo.toml, Cargo.lock, rust-toolchain.toml, src/) and of the PTX. It uses the published backend
  (`~/.cargo/cuda-oxide/librustc_codegen_cuda.so`) so cargo-oxide never builds inside `../cuda-rust`.
- **Policy: checked-in artifact, verified by hash.** sysone's `build.rs` embeds each artifact whose manifest matches
  the current sources and the PTX file. A stale or mismatched artifact is embedded as an error (and printed as a
  cargo warning); a missing one is simply absent. Selecting the SIMT backend then fails at run time with the exact
  rebuild command; nothing falls back to cuTile silently. Chosen over running cargo-oxide from `build.rs` because a
  nested cargo under the 1.98.0 build would need a second toolchain, a CUDA toolkit and the codegen backend on every
  machine that builds sysone, and a build script that sometimes rebuilds kernels makes builds depend on the host.
- Run time: `src/kernels/simt.rs` loads the PTX for the device's exact architecture once per device (the driver
  caches the JIT) and launches with cuda-async's `AsyncKernelLaunchBuilder` on the same stream as the cuTile
  kernels. Other architectures need their own artifact (`build.sh sm_100a`); arch is a parameter, not hard-coded.

## cuda-oxide notes (nothing modified upstream)

1. Loops around the `mma.sync` intrinsics are not unrolled by cuda-oxide's `opt -O2` (the intrinsic lowers to
   `asm sideeffect`), so register arrays indexed by the loop variable are demoted to local memory. Repro: a kernel
   with `let mut acc = [[0f32; 4]; 8]; for n in 0..8 { acc[n] = mma_m16n8k16_f32_bf16(acc[n], a, b) }` compiles to
   one `mma.sync` in a loop and a 128-byte `__local_depot`. Worked around with an `unroll!` macro (constant index
   per copy).
2. `cuda_core::Function::set_max_dynamic_shared_memory_bytes` is `pub(crate)`; raising the dynamic shared memory
   limit of an untyped (PTX-loaded) kernel needs `cuFuncSetAttribute` on `Function::cu_function()` directly
   (`SimtModule::function`).
3. `cargo oxide build` in a project with a path dependency on the cuda-rust checkout builds the codegen backend in
   place inside that checkout unless `CUDA_OXIDE_BACKEND` points at the published `.so`; `build.sh` sets it.
4. `f32::exp` lowers to libdevice's accurate `expf` (range reduction + `ex2.approx`, ~2 ulp), not `__expf`; noted
   because it rules out the fast exp as a source of the prefix-0 error above.
