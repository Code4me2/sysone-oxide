# F1: a faster NVFP4 forward (2026-11-14)

Workstream F1 (branch `ws/f1-nvfp4-speed`): measure the forward first ([PROFILE.md](PROFILE.md)), then make the
nvfp4 engine faster without changing a single output bit. Result on GB10: the nvfp4 forward is **1.10x faster at
16k** (2,199 → 2,003 ms per replayed step, 7,450 → 8,177 packed tok/s, measured back to back against the N1 build)
and 1.10-1.13x at 1k-32k; the nvfp4 engine is now **1.65x the bf16 engine** at 16k (N1: 1.48x). Every change is
byte-identical to N1 (kernel tests, the engine's logits on 42 corpus batches, and all 278 eval responses), so no
accuracy gate moved. The bf16 engine is unchanged within run-to-run noise.

## What changed

1. **SiLU·mul + quantize in the gate/up GEMM epilogue** (`kernels::nvfp4::gemm_nvfp4_swiglu_il`,
   `GraphOp::GemmNvfp4SwiGlu`). N1 ran the gate/up FP4 GEMM into a bf16 `[T, 24576]` tensor and then
   `silu_mul_nvfp4` over it (805 MB written and read again per layer at 16k). The fused kernel keeps the plain
   GEMM's main loop exactly (one accumulator, one 128-row weight tile per k-step, the same `mmaf_scaled` chain per
   output element) and applies, in its epilogue, the GEMM's own `bf16(acc · alpha)` per half followed by
   `silu_mul_nvfp4`'s operations (`bf16(bf16(silu(g)) · u)`, NVFP4-quantized under the down projection's input
   scale). For one weight tile to hold the gate *and* up rows of the same product columns, `GpuEngine::load`
   interleaves each gate/up weight's rows in blocks of 64 (`ModelWeights::interleave_gate_up_nvfp4`: a row
   permutation of the packed values and of the scales, no value changes; `Linear::Nvfp4::gate_up_block`). The
   plain `gemm_nvfp4` refuses such a weight, and the forward builder refuses a layout/fusion mismatch.
2. **Two fused-GEMM tile blocks per SM** (cuTile `occupancy` hint 2): one tile's epilogue (exp, two IEEE
   divisions, group reductions) then runs under the other tile's MMAs. Without it the fused GEMM is 16.3 ms at
   16k; with it 13.2 ms, the plain gate/up GEMM's own time, i.e. SiLU·mul + quantize became free.
3. **Occupancy hints on the memory-bound kernels** (`engine::kernels::KernelTuning`): `add_zc_rmsnorm` and
   `add_zc_rmsnorm_nvfp4` at 2 tile blocks per SM (one 4096-wide row per block; the compiler's default of 255
   registers allowed only one), `silu_mul_nvfp4` at 3 (used when the fused GEMM is off). `KernelTuning::N1`
   restores the compiler defaults.
4. **Tooling**: `scripts/profile/nsys_forward.py` and `ncu_summary.py` (PROFILE.md); `bench_nvfp4_mlp` (every
   variant above, compile hints on the GEMMs, the norms); `bench_forward --nvfp4-separate-silu --n1-tuning` and
   `sysone --nvfp4-separate-silu` (N1's launches in the same build, for A/B runs and diagnostics).

The bf16 engine shares only change 3 (`add_zc_rmsnorm`, 64 launches per forward).

## Speed

### Forward (`bench_forward --tokens 1024,4096,16384,32768`, idle GPU, lock held, SIMT GDN)

The GB10's sustained clock moves by a few percent between runs (power cap, temperature): the N1 build measured
2,136 ms at 16k at 04:15 and 2,199 ms at 06:15 with the same binary. So the before/after pairs below were run back
to back in one session (N1 build from `6183295`, F1 build), and the comparison is between them.

| bucket (packed T) | N1 replay ms | F1 replay ms | speedup | N1 packed tok/s | F1 packed tok/s |
|---|---:|---:|---:|---:|---:|
| 1,024 (604) | 146.0 | **129.6** | 1.13x | 4,138 | **4,659** |
| 4,096 (3,624) | 588.6 | **533.3** | 1.10x | 6,157 | **6,796** |
| 16,384 (16,377) | 2,198.8 | **2,002.9** | 1.10x | 7,448 | **8,177** |
| 32,768 (32,186) | 4,318.5 | **3,913.2** | 1.10x | 7,453 | **8,225** |

(A second N1 run after the F1 run gave 145.9 / 592.2 / 2,198.1 / 4,310.4 ms.) bf16 in the same session: 3,312.7 ms
at 16k (4,944 tok/s), so **nvfp4 / bf16 = 1.65x** at 16k (N1: 1.48x) and 1.66x at 32k.

Where the 196 ms at 16k come from (per-op profile, eager, CUDA events, ms per forward):

| op | N1 | F1 | Δ |
|---|---:|---:|---:|
| gate/up FP4 GEMM + `silu_mul_nvfp4` → fused GEMM (32) | 432.1 + 204.5 = 636.6 | 442.8 | **-193.8** |
| `add_zc_rmsnorm_nvfp4` (32) | 76.1 | 58.0 | -18.1 |
| `add_zc_rmsnorm` + first norm (33) | 79.9 | 72.0 | -7.9 |
| everything else | 1,399.1 | 1,434.5 | +35.4 (unchanged kernels: run-to-run clock variation, mostly in the cuBLAS GEMMs) |
| total (profiled eager forward) | 2,191.7 | 2,007.3 | -184.4 |

At 1k / 4k / 32k the same three rows save 13 / 51 / 438 ms of op time.

**bf16** (A/B in one session): 4k 967.1 → 948.6 ms, 16k 3,312.7 → 3,316.0 ms: unchanged within noise. Its 64
residual-add norms got 15 ms faster at 16k (157.3 → 142.6 ms), but its cuBLAS GEMMs vary by more than that from
run to run (the MLP down GEMM took 586 ms in the morning and 710 ms in both builds in the afternoon; workstream L1
pins cuBLAS algorithms).

Memory: the arena for buckets up to 32k is 1.96 GiB instead of 2.07 GiB (the bf16 gate/up value is gone; the
planner's peak is elsewhere, in the GDN in-projection's output).

### What did not help (measured, not kept)

- **FP4 GEMM tile per M**: `bench_nvfp4 --sweep` at 1k/4k/16k/32k (5 tile shapes x 3 group sizes x 3 persistence
  settings): 128x128x128 grouped-M 8, non-persistent, is the fastest cuTile configuration for both MLP GEMMs at
  every M. Tiles stay fixed (and would not affect batch invariance anyway: BM/BN/grouping change no bit).
- **k-tile-major block scales** (PROFILE.md opportunity #2): removes the 25% of L2 traffic wasted on scale
  sectors, but the GEMM is not faster (gate/up 4k 3.24 → 3.33 ms, down 1.74 → 1.88 ms): it is pipeline-bound,
  not L2-bound (PROFILE.md addendum).
- **Compile hints on the plain FP4 GEMM** (4k gate/up, default 3.31 ms): 4 warps 3.23, 8 warps 3.87, occupancy 1
  3.28, occupancy 2 3.82, 8 warps + occupancy 2 4.23 ms; 16 warps is rejected by the compiler.
- **PDL**: ≤ 0.15% of the forward to gain (PROFILE.md (c)); not implemented.

## Bulk (`sysone bulk --engine nvfp4`, 2,000-document corpus, seed 1)

Corpus: `sysone bulk gen --docs 2000` (seed 1: 6,303,460 packed tokens, 20,078 decisions; BULK.md), bulk defaults
(window 1,024, steps up to the profile's 32,768-token bucket), idle GPU. The N1 build and the F1 build back to back:

| | N1 build (`6183295`) | F1 build | |
|---|---:|---:|---:|
| wall time (s) | 913.6 | **838.5** | |
| docs/s | 2.21 | **2.42** | **+9.5%** |
| decisions/s | 22.19 | **24.29** | +9.5% |
| packed tok/s | 6,966 | **7,626** | +9.5% |
| steps / padding / GPU busy | 202 / 0.20% / 99.99% | 202 / 0.20% / 99.99% | |
| worker load (s) | 8.7 | 11.9 | (+3.2 s: the gate/up row interleave at load) |

`sysone bulk compare n1.jsonl f1.jsonl`: **2,000 of 2,000 result bodies identical** (64,723 probabilities, dp max 0,
no status or field mismatch): bulk's step sequence is deterministic and the engine is byte-identical, so the two
builds wrote the same answers. For scale, bf16 bulk on the same corpus measured 1.61 docs/s and 5,062 packed tok/s
in B1 (BULK.md, a different day): nvfp4 with F1 is ~1.5x that.

The interleave costs 3.2 s once per engine load (a host round trip of the 96 gate/up tensors, 1.6 GB); a
device-side permutation would remove it if load time ever matters.

## Remaining opportunities (in order)

1. **A hand-written FP4 GEMM** (cuda-oxide, `mma.sync` block-scaled e2m1): the cuTile kernel holds the tensor pipe
   at ~55% and no cuTile knob moves it; both MLP GEMMs plus the fused GEMM are 668 ms of the 2,003 ms forward at
   16k. A deeper explicitly pipelined kernel (cp.async/TMA staging, warp-specialised producer, 2 CTAs or a
   128x256 tile per SM) at ~75% tensor-pipe use would save ~150-200 ms (7-10%). Bit identity needs the same
   per-element MMA chain (same instruction, same K order) and the same epilogue; the F1 kernel tests are the
   harness for it.
2. **Residual add in the down GEMM's epilogue** (PROFILE.md #4): ~18 ms at 16k (0.9%); the next layer's norm then
   reads one tensor instead of two.
3. **Outside F1's scope**: the bf16 cuBLAS projections (~770 ms at 16k; L1), the GDN scan (~190 ms) and its
   `gated_rmsnorm` (65 ms at 166 GB/s, the same one-block-per-SM pattern the norms had: an occupancy hint there is
   likely worth ~15 ms, but it lives in `kernels/gdn`).
4. **sm_120** (x86 T8 in docs/x86/TASKS.md): every F1 choice was tuned on GB10; the hints are per-launch constants
   in `KernelTuning::DEFAULT`, so a card that prefers other values gets its own constants.
