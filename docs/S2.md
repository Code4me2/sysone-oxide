# S2: two small speedups, bit-identical (2026-11-14)

Workstream S2 (branch `ws/s2-small-fixes`): two launch changes that move no output bit. On GB10 the nvfp4 forward
is **2.5-3.8% faster at 16k** (1,968-2,002 → 1,893-1,920 ms per replayed step, 8,179-8,320 → 8,529-8,650 packed
tok/s) and **3.3% faster at 32k** (3,851 → 3,722-3,725 ms), measured back to back against a build of main
(`18ccb31`). The bf16 engine gains 1.2-2.0% at 16k and 0.9-1.1% at 32k (only change A applies to it). Every
change is bit-identical to main: kernel tests, the engine's logits on 42 corpus batches (eager and replayed, both
engines, both GDN backends) and every kind of debug tap. Every gate passes unchanged, with the same numbers as main.

## What changed

**A. GDN `gated_rmsnorm`: one token's 32 heads per tile block** (`kernels::gdn::GatedNormTiles`,
`gated_rmsnorm_with`, new kernel `gated_rmsnorm_hb`; `KernelTuning::gated_norm`). The kernel normalised a
`[16 tokens, 128]` tile of one head per tile block (grid `T/16 x 32`). `gated_rmsnorm_hb` loads a `[BR, HB·128]`
tile (HB adjacent heads), reshapes it to `[BR·HB, 128]` and runs exactly the old kernel's operations on it, so
every element gets the same value; only the memory access shape changes. The engine now launches `BR = 1, HB = 32`:
one whole 4096-wide row per tile block, like the residual norms. Both GDN backends run this kernel (SIMT is the
default on sm_121, cuTile elsewhere); the change is the same for both.

projection):

Occupancy hints alone do not help at 4k-32k (the old launch was not register-bound in the way the residual norms
were: its 16-row tiles were small, and the row tiles of 256 bytes per head are the limiter); wider tiles do. 1 x 32
at compiler defaults is the fastest or within 0.5% of it at 4k-32k, and at 239 GB/s it is at the 243 GB/s that
hwprobe measures for LPDDR5X; occupancy 2 is 6% faster at 1k (0.004 ms per launch) and slower at the buckets bulk
tagging runs at, so it stays off. Warps-per-CTA hints of 1 and 2 are rejected by the compiler.

In the engine (per-op profile, eager, 24 launches, ms per forward): 16k **61.5-63.6 → 40.0-40.5**, 32k 130.7-133.1 →
80.6-81.2, 4k 15.5-16.9 → 10.1-10.4, 1k 3.6-3.7 → 2.3. That is 2.6 ms per launch before (it runs right after the
GDN scan) and 1.7 ms after: -22 ms at 16k, more than the ~15 ms expected.

**B. Residual add in the NVFP4 down GEMM's epilogue** (`kernels::nvfp4::gemm_nvfp4_raw_residual`,
`GraphOp::GemmNvfp4Residual`; `EngineOptions::nvfp4_residual`, default on; `--nvfp4-separate-residual` restores
main's launches). Before, the down GEMM wrote `mo = bf16(acc · alpha)` and the next layer's `add_zc_rmsnorm` read the
residual and `mo`, wrote `r = bf16(f32(r) + f32(mo))` and normed it. Now the GEMM's epilogue computes the same
`bf16(acc · alpha)` (the raw GEMM's main loop and rounding, unchanged), loads the residual tile, adds exactly as
`add_zc_rmsnorm` does (one f32 addition of the two bf16 values, one rounding to bf16) and stores the residual in
place; `mo` is never written. The norm that followed becomes `GraphOp::ZcRmsNormRes`.

- **`zc_rmsnorm_res`, not `zc_rmsnorm`.** The plain `zc_rmsnorm` kernel (layer 0's input norm) on the updated
  residual is *not* bit-identical to `add_zc_rmsnorm`'s norm: 1 of 1.2 M and 10 of 4.2 M outputs differ by one bf16
  ulp (`kernels_s2::down_gemm_residual_then_norm_is_bit_identical_to_gemm_then_add_norm`, reported). Its source is
  the same arithmetic, so the compiler lowers its row reduction differently (it loads the row through a `[-1, N]`
  partition instead of the `[1, N]` per-block view). `norm::zc_rmsnorm_res` is `add_zc_rmsnorm` with the add
  removed (same parameter layout, same loads, same norm code) and matches it bit for bit.
- **Shared by every layer and the trimmed layer**: `forward::mlp_block` takes a `fuse_residual` flag and returns the
  residual after the add (and no `mo`) when it applies; the trimmed last layer uses the same block on `Dim::Answers`
  values and then `ZcRmsNormRes` as its final norm; the untrimmed forward ends the same way.
- **Debug taps**: a layer whose sublayer taps are requested (`Taps::sublayers`: `mix{i}`, `mid{i}`, `mlp{i}`), or the
  trimmed layer with `Taps::answer_rows` (`mid{i}_a`, `mlp{i}_a`), keeps the separate add, so those values exist and
  are what they were. `layer{i}` taps of fused layers copy the residual after the GEMM's add (the same value as
  before, taken one op earlier).
- **bf16 projections**: not applied. The bf16 down projection, `o_proj` and the GDN `out_proj` are pinned cuBLASLt;
  its `beta = 1` epilogue (`D = alpha·AB + beta·C`) computes `acc + f32(r)` and rounds once, whereas the reference
  rounds the GEMM output to bf16 first (`bf16(f32(r) + f32(bf16(acc)))`); the double rounding cannot be expressed,
  so the result would not be bit-identical. Likewise `o_proj` / `out_proj` in the nvfp4 engine (bf16 cuBLASLt).
- **Memory**: the arena for buckets up to 32k is 1.75 GiB instead of 1.96 GiB (no `[T, 4096]` MLP output).

The epilogue's residual load comes after the main loop (one tile block per SM, so it is not hidden): +0.6 ms per
launch at 16k against the -1.1 ms the norm saves. Loading the residual tile before the main loop was slower (7.33 vs
7.15 ms at 16k, register pressure); an occupancy hint of 2 on this GEMM is 1.7x slower (as on the plain FP4 GEMM in
F1). In the engine the residual GEMM costs a little more than in isolation (+0.8-0.9 ms per launch at 16k), so the
measured saving of B is smaller than the ~18 ms expected: down GEMM + norm 282.0-286.7 → 275.2-276.9 ms at 16k
(**-7 to -12 ms**), 568.2-571.5 → 544.7-548.0 at 32k (-23 ms), neutral at 4k (68.3-69.7 → 68.9-69.3) and -0.5 ms at 1k.

## C1 and S2 (merge, 2026-11-14)

C1 (docs/C1.md) moved the NVFP4 down projection to cuBLASLt on sm_121. cuBLASLt's `beta = 1` epilogue rounds
`alpha·acc + residual` once, while the engine (and `gemm_nvfp4_raw_residual`) rounds `bf16(bf16(acc·alpha) + r)`, so
the residual add cannot move into a cuBLASLt GEMM bit-identically. The engine therefore fuses the residual add (part B)
only when the down GEMM runs on cuTile (`nvfp4_residual && !fp4_lt` in `GpuEngine::load`); part A (`gated_rmsnorm`)
applies everywhere. `s2_launches_equal_f1_launches` pins both of its engines to `--fp4-gemm cutile` so it keeps
exercising part B on GB10.

Which is faster on GB10, measured on the merged build (`bench_forward --tokens 4096,16384,32768 --no-profile`, nvfp4,
idle GPU, one lock session, runs alternated twice; replay medians in ms):

| bucket | cuBLASLt down (default; residual add in the norm) | cuTile down + fused residual add | cuTile down, add in the norm |
|---|---|---|---|
| 4k | 496.7 / 509.3 | 516.3 / 522.4 | 519.9 |
| 16k | 1,825.5 / 1,858.4 | 1,913.0 / 1,919.1 | 1,930.8 |
| 32k | 3,600.4 / 3,642.2 | 3,747.0 / 3,746.4 | 3,790.1 |

cuBLASLt down is 3-5% faster at 16k than the best cuTile configuration, so it stays the sm_121 default (8,810-8,970
packed tok/s at 16k, against 8,523 before C1 and S2). The fused residual add is worth 0.6-1.2% where cuTile runs the
down GEMM (sm_120 until T8 measures cuBLASLt there).

Review note: a back-to-back rerun by the reviewer put S2's gain over main at 1.5-2.2% at 16k (main 1,948-1,950 ms, S2
1,907-1,919 ms) and 0.8-2.4% at 32k; the larger figures in the table below compare against slower-than-usual main runs.

## Remaining opportunities

1. **The residual GEMM's epilogue** costs 0.6-0.9 ms per launch at 16k because the residual load is serialised after
   the main loop with one tile block per SM. A hand-written FP4 GEMM (F1 opportunity #1) with a producer warp could
   prefetch the residual tile during the last k-steps; that would make B worth the full ~35 ms at 16k it saves in the
   norm.
2. **The other GDN cuTile kernel at the bandwidth limit**: `tree_conv1d_silu` (62 ms at 16k) is next in size among the
   memory-bound kernels; the same tile-shape sweep could apply.
3. **bf16 residual adds** after cuBLASLt projections stay separate (bit identity, above). A batch-invariant own bf16
   GEMM (L1 open item 1) could carry the same epilogue.
4. **sm_120** (x86): the gated-norm tile and the residual GEMM were measured on GB10 only; `KernelTuning` holds the
   choice per launch, so a card that prefers another shape gets its own constants (bit-identical either way).
