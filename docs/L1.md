# L1: batch invariance (pinned GEMMs) and last-layer trimming (2026-11-14)

Workstream L1 (branch `ws/l1-trim-pin`). Two engine changes, both on by default, both behind `EngineOptions` flags:

- **B. Batch invariance.** `EngineOptions::gemm = GemmMode::Pinned` (`--gemm pinned|heuristic`): the bf16 GEMMs run
  one cuBLASLt algorithm per weight shape at every T, without split-K. Together with one fix outside cuBLAS
  (`qk_norm_rope` one token per tile block, below) **every branch is now bit-identical alone and packed, in both
  engines**: 164/164 branches packed vs alone and 155/155 alone in a 4x larger bucket, bf16 and nvfp4 (N1: 103/164
  and 134/155).
- **A. Last-layer trimming.** `EngineOptions::trim_last_layer` (`--no-trim-last-layer` turns it off): the last layer
  (index 31, full attention) computes keys and values for every token but its queries, attention, `o_proj`,
  residual add, post-norm, MLP and the final norm only for the answer rows. With pinned GEMMs the trimmed logits are
  **bit-identical** to the untrimmed ones (86/86 steps, 526/526 answer rows, both engines).

Every existing gate passes unchanged (no gate, threshold or tolerance was touched). At 16k packed tokens the forward
is 1.9% (bf16) and 1.5% (nvfp4) faster than main; at 4k 6.4% / 1.3% faster; at 1k 5.5% / 2.1% slower (pinning
costs more than trimming saves at the smallest bucket; numbers below).

## What changed

### Pinned GEMMs (`src/engine/gemm.rs`, ARCHITECTURE §3.6)

`Blas::with_mode(stream, GemmMode::Pinned)` holds a cuBLASLt handle next to the cuBLAS one. Per weight shape (N, K,
the row strides of x and y, bf16 or f32 output) it asks cuBLASLt's heuristic for up to 32 candidates at
`PINNED_REF_ROWS` = 16,384 rows (the bucket where the GEMMs cost most), with the byte alignments the strides
guarantee declared as minimums, and keeps the first candidate with `SPLITK_NUM <= 1` and no reduction scheme. That
algorithm is used for every T (B / C layouts per T are created once and checked with `cublasLtMatmulAlgoCheck`, before
any graph capture). Compute type fp32, scale type fp32, one output rounding: the same numerics as `cublasGemmEx`
with `CUBLAS_COMPUTE_32F`. The choice depends only on the weight shape, so it is the same in every bucket and every
engine configuration. Chosen on GB10 (ids are cuBLASLt's): `[12352|24576, 4096]` and `[4096, 12288]` algo 67 (tile
412, stages 35); `[4096|8192|2048, 4096]` algo 21 (tile 23, stages 9); the f32 slot readout algo 23.

`GemmMode::Heuristic` is the previous `cublasGemmEx` path, kept as an option (`--gemm heuristic`).

### `qk_norm_rope` one token per tile block (`kernels::attention::ROPE_TOKENS` 2 -> 1)

With pinned GEMMs, packed vs alone was still 119/164 (max |dp| unchanged at 1.10e-2). `engine_e2e::packing_diagnostic`
(ignored; compares every layer's taps of a request alone and packed after another) located the first difference in
the q output of `qk_norm_rope` (layers 3, 7, 27) on 1-2 rows of a request, always when the request was packed after an
odd-length one. With two tokens per tile block, a token's q norm rounded differently on ~0.05% of rows depending on
whether it was the first or second row of its block, i.e. on the parity of its position in the packed stream
(`kernels_attn::qk_norm_rope_rows_do_not_depend_on_their_position`: shifts by 1 and 3 rows changed 2/4096 q rows).
One token per block removes the dependence (0/4096 at every shift). Kernel accuracy vs the f64 reference is
unchanged (q and k max 1.5 bf16 ulp, mismatched 0.0063% / 0.0068%, tolerance 2 ulp / 1%). Cost: within noise (the
`attn.qk_norm_rope` class is ~18 ms at 16k in both builds).

### Last-layer trimming (`src/engine/forward.rs`, ARCHITECTURE §3.5)

`forward::build_opts` with `ForwardOptions::trim_last_layer` writes the last layer as `trimmed_last_layer`:

```text
hn, x  = add_zc_rmsnorm(x += m30, ln1)        every token (unchanged)
kv     = hn · [Wk; Wv]ᵀ                        every token
_, k   = qk_norm_rope(<unwritten>, kv)          every token: the unchanged kernel; its q input is GraphOp::Uninit
hn_a   = hn[answer_rows]; qg_a = hn_a · Wqᵀ     [Q, 8192]
q_a, _ = qk_norm_rope(qg_a, kv[answer_rows])    at the answer rows' positions (new metadata array answer_pos)
o_a    = seg_attn(q_a | k, kv | gate qg_a) · Woᵀ   AttnPlan::answers: one work item per answer row
x_a    = x[answer_rows]; post-norm, MLP (bf16 or NVFP4 as the checkpoint), final norm, slot readout on [Q, ..]
```

- New ops: `QkNormRopeAnswers`, `SegAttnAnswers`, `Uninit`; `Kernels::{qk_norm_rope_answers, seg_attn_answers}`;
  `AttnPlan::answers`; `DeviceMeta::answer_pos`.
- A first version used a separate k-only RoPE kernel; on real data it differed from `qk_norm_rope`'s k on 1-5 rows per
  request (`engine_e2e::trim_diagnostic`, which compares the trimmed path's answer-row taps, `Taps::answer_rows`, with
  the untrimmed taps). It was removed: the trimmed layer runs the unchanged `qk_norm_rope` over every token with an
  unwritten query input and keeps only k (`kernels_attn::qk_norm_rope_k_ignores_q_and_gathered_rows_match_bits`: k is
  unchanged by NaN / 3e38 queries). This costs the q half of one RoPE launch but not the Q GEMM over every token.
- Debug taps that need the last layer's rows (`Taps::norm`, the last layer in `Taps::layers`) turn trimming off
  (`forward::can_trim_last_layer`; `engine_layers` runs untrimmed and logs it). The MLP ops of the trimmed layer
  repeat the per-layer MLP on `Dim::Answers` values in a separate function, so the per-layer loop (where F1 works) is
  untouched apart from the debug taps of attention layers (`k{i}`, `q{i}`, `attn{i}` with `Taps::sublayers`).
- **Answer capacity per bucket.** Trimming only helps if the `[Q, ..]` values are smaller than `[T, ..]`. A bucket's
  answer capacity was `min(T, max_answers)` (1,024 at T = 1k, i.e. no saving); it is now
  `min(ceil(T / tokens_per_answer), max_answers)` with `EngineOptions::tokens_per_answer = 8`
  (`BucketPlan::with_answer_density`, `contract::bucket_answers`): 128 / 512 / 2,048 answers at 1k / 4k / 16k. Every
  branch's suffix carries at least the chat template's closing tokens, so real batches stay far below one answer per
  8 tokens; a denser batch runs in the next larger bucket. `StepLimits::tokens_per_answer` passes the capacity to
  `sysone bulk`'s packer (and through the worker `Hello`, defaulting to 1 for older peers).

## Bit-identity

| check | bf16 | nvfp4 |
|---|---|---|
| packed vs alone (16k budget): branches bit-identical; max \|dp\| | **164/164; 0** (N1: 103/164; 1.10e-2) | **164/164; 0** (N1: 103/164; 7.93e-2) |
| alone vs alone in a 4x larger bucket | **155/155; 0** (N1: 134/155) | **155/155; 0** (N1: 134/155) |
| trimmed vs untrimmed, pinned GEMMs (43 batches eager + replay) | **86/86 steps, 526/526 rows** | **86/86 steps, 526/526 rows** |
| trimmed vs untrimmed, heuristic GEMMs (reported) | 62/86 steps, 456/526 rows, max \|dlogit\| 1.36e-3 | 86/86 steps, 526/526 rows |
| untrimmed, pinned vs heuristic GEMMs (reported) | 10/86 steps, 252/526 rows, max \|dlogit\| 5.5e-5 | 10/86 steps, 252/526 rows, max \|dlogit\| 5.5e-5 |
| graph replay vs eager; fused vs standalone quantize | bit-identical | bit-identical; 84/84 |

With cuBLAS's heuristic, trimming is not bit-identical in bf16: the Q, O, MLP and readout GEMMs see M = Q instead of
M = T, and cuBLAS picks other kernels for the smaller M (the nvfp4 engine happened to match on this corpus). With
pinned GEMMs a row's GEMM result does not depend on M (`engine_gemm::pinned_gemm_rows_do_not_depend_on_the_batch`:
0 of 3,551 sub-batch rows differ for every engine shape; the heuristic mode differs on 1-1,503 of them, mostly at
M = 1 and for the f32 readout).

- **Pinning** costs 5-6% at 1k (the 16k-tuned tiles are too large for 1k rows), is neutral at 16k and faster at 4k
  in bf16 (cuBLAS's own 4k choice was worse). Throughput work runs at the largest buckets, so it stays the default;
  `--gemm heuristic` gives the old speed (and the old batch dependence) at small buckets.
- **Trimming** at 16k (per-op profile, pinned): AttnQ 109.5 -> 93.1 ms, AttnO 56.0 -> 46.5, the FP4 MLP GEMMs
  643 -> 632, SiLU·mul + quantize 206 -> 202, attention 36.4 -> 32.4 (nvfp4); in bf16 the MLP GEMMs save 78 ms. That is
  the last layer's 1/32 share of these ops times (1 - 2,048/16,384); the answer capacity (2,048 at 16k) bounds it,
  not the 81 real answers. The profile's TFLOP/s column counts T rows for every launch, so it overstates the
  trimmed layer's GEMMs.
- First step (JIT and cuBLASLt plans) at 1k: bf16 4.3 s (main 4.7), nvfp4 6.7 s (main 6.2).

## Open items

1. Pinned GEMMs at small buckets: a per-shape algorithm chosen at, say, 2k rows, or a cheaper choice for small M, would
   recover the 1k cost, but any per-bucket choice breaks bit-identity across buckets. A batch-invariant own bf16 GEMM
   (mma.sync, fixed tiles) is the other route.
2. Answer capacity: `tokens_per_answer = 8` is a conservative bound; a capacity closer to real batches (e.g. T/64 at
   16k) would cut the trimmed layer further (~2,048 -> ~256 rows), at the cost of moving answer-dense batches to the
   next bucket. Needs a decision on the bound and bulk's packing.
3. sm_120 (x86): pinned algorithms are chosen per device; the row-invariance test (`engine_gemm`) and the
   batch-invariance gate should run there (x86 T-task) before relying on bit-identity across machines (pinned algorithms
   make results invariant to the batch on one device, not identical across devices).
